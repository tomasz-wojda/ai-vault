## 5. CREATE AND UPDATE PROTOCOL

+ canvas_create_from_svg and canvas_update_from_svg are the only tools that can be used to edit a board from a <svg> composition.
+ on the first call, use canvas_create_from_svg to upload the <svg> composition to a Miro board which already manages composition placement and collision avoidance, so no need to fetch the full board state for that
+ after canvas_create_from_svg, use canvas_update_from_svg in subsequent calls to iterate over the created composition.
+ some widgets expand automatically, so their final dimensions may differ from those authored in the SVG. canvas_create_from_svg and canvas_update_from_svg stamp their estimated dimensions into result_svg and report the ids whose dimensions changed.
+ REQUIRED: whenever a call reports changed dimensions, immediately check those widgets in result_svg and reposition affected widgets with canvas_update_from_svg. Do not report completion until spacing is consistent and all resulting overlaps are resolved, leave a reasonable margin as a buffer in case the estimates are not exactly correct.
+ canvas_update_from_svg is additive: removing a widget from the SVG does NOT delete it from the board.
+ for iterating over an existing <svg> composition the canvas_update_from_svg tool can be used to apply the changes to the board.
+ To EDIT an existing widget: keep its data-miro-id exactly as it came back in the previous result_svg, and change only the attributes you want (text, color, position, ...). For a position-only expandable widget update, send only data-type, data-miro-id, x, and y. Matching is by data-miro-id.
+ PATCH SEMANTICS (stickies, shapes, text, cards, frames, images, custom widgets): on an element carrying data-miro-id, an OMITTED attribute keeps its current board value - only the attributes you write are applied. So a color-only change can be a minimal stub: <rect data-miro-id="30123" data-type="sticky" data-color="yellow" />. CLEARING TEXT: data-content="" empties a sticky's or a shape's text; a card's text is data-title / data-description (data-description="" clears the description); a text widget (<text> or <textArea>) is removed by deleting it, not by blanking its body. GEOMETRY: x and y move text and custom widgets without restating size; width and height resize a custom widget without restating position. For other items, restate the full box from the latest result_svg. A frame's geometry needs its transform plus the background rect's width/height, and a frame keeps its live title unless you write a NON-EMPTY data-frame (data-frame="" on a sparse wrapper never wipes the title). An <image>'s height always follows the source's aspect ratio, so an authored height that disagrees is ignored, and swapping href alone re-sizes the image to the new source's natural size around its center - restate the bbox on the same element to pin a footprint. ALWAYS keep the element's type markers on a stub (data-type="sticky", data-widget-type="card", the <text>/<textArea> tag): a bare <rect> reads as a plain shape, and a partially-authored stub whose type does not match the live widget is reported as a failed item naming both types. Keep sparse elements in their original frame <g>. Body-carried payloads follow the same rule: a code widget's body IS its content, so a stub with an empty body keeps the live code (data-title alone just renames the caption), and writing a body replaces it; the same holds for poll/spinner/dropdown option lists. Connectors require full restating; a table follows the tables format skill; dynamic_poll is CREATE-ONLY and an id-matched edit to one is reported as a failed item.
+ PARTIAL BODY EDITS (docs, code, diagrams, html_content): to change part of a long body, never resend the whole body. Send the type-marked stub with its data-miro-id and one <edit> child per change instead of the body: <foreignObject data-type="doc" data-miro-id="30124"><edit><old>exact current text</old><new>replacement</new></edit></foreignObject>. <old> and <new> are taken verbatim, so never indent them to line up with the XML; copy <old> from the latest read, the result_svg, or the edits you already sent (markdown source for a doc; wrap HTML in <![CDATA[ ... ]]>) and must match exactly once; an empty <new> removes it; to insert, put a nearby anchor in <old> and the anchor plus the new text in <new>. Edits apply in order. A missing or ambiguous <old> fails only that widget, none of its edits apply, and failed_items names the closest live text; the rest of the call applies. Other widgets do not take <edit>. The result_svg echoes the element's geometry, not its body.
+ To ADD a new widget: leave data-miro-id OFF entirely (just give it a local `id` if a connector needs it). canvas_update_from_svg creates it and returns its assigned data-miro-id in the result_svg, which you reuse on the next iteration.
+ To DELETE a widget: keep its data-miro-id and add data-deleted="true" to the element. A minimal stub is enough - e.g. <rect data-miro-id="3458764515349839821" data-deleted="true" /> - you do NOT need to reproduce the element's other attributes. Deletion is explicit and per-element: only elements carrying data-deleted="true" are removed; simply dropping an element from the SVG never deletes it. Only widgets created through this tool (managed) can be deleted; placeholders and foreign items are read-only and a marker on them is refused. Connectors delete the same way (data-deleted="true" on the <line>/<path> with its data-miro-id).
+ An element with data-read-only="true", including everything inside it, is context only. Do not create, edit, move, or delete it. Omit it from update SVG.
+ data-locked="true" marks a widget a user locked on the board ("protected": only a board owner can unlock it). Do not edit, move, resize, or delete it; the attempt is refused as a failed item. Unlike data-read-only, its children stay editable and new children may be added inside it. If the user wants it changed, tell them to unlock it in Miro. data-group is the id of the user-made group it belongs to. Both are server-stamped: never author them.
+ CONFIRM BEFORE DELETING: deletion is destructive and cannot be undone through this tool. Before sending any SVG that contains data-deleted="true", confirm the specific items to remove with the user first.
+ ITERATION RULE: always start from the most recent result_svg, edit it in place, and feed it back. Do not regenerate the SVG from scratch and do not transcribe ids from memory.
+ An update's result_svg returns each edited widget in the form you sent, carrying the board's values: a stub comes back a stub, and any geometry you wrote comes back as the full box. Omitted attributes are not restated; call canvas_read_as_svg when you need a widget's full current state. A create or update result_svg leaves out each body you sent, which you already hold.
+ A data-miro-id that does not exist on the board is reported as a FAILED update for that element (likely a stale or invented id) - it is never silently created as a duplicate. So only ever reuse ids from a prior result_svg; if you are unsure of the current ids, call canvas_read_as_svg.
